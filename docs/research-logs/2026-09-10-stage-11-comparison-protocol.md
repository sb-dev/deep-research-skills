# Stage 11 comparison protocol

Recorded before producing the four comparison outputs in this continuation. Authority: bootstrap section 17, actual core-versus-pack behaviour, and Stage 10 command contracts. This is an in-session execution of proposed procedures on real public sources, not an installed-skill trial or a provider benchmark.

## Conditions and fixed inputs

There are two tasks and two conditions per task: the accepted core procedure with no pack, and the same core procedure with the selected profile. The source universe, question, disclosure authority and output purpose are fixed within each pair. A profile may cause deeper inspection or different organisation of that universe; it cannot acquire an unrelated corpus or change the question. Baseline source findings cannot be intentionally suppressed to make a pack look better.

SCH task: assess what RULER establishes about relying on an advertised context window for a research assistant. Public author sources: arXiv 2404.06654, its v2 and v3 representations. Scope is this work and its revisions, not an exhaustive literature review. Do not run models, approve a product or infer current model rankings. Core source observations already available at protocol time include the different model counts in v2/v3 and the context-dependent threshold. Both conditions may use them.

OSS task: assess whether langchain-ai/open_deep_research at commit 1b7d2e80db9faa586165c60e09096dbbfd483a64 is a candidate optional execution engine, using its README, LICENSE, pyproject.toml, configuration.py, langgraph.json, commit metadata and supervisor_tools implementation. Scope is static integration assessment. Do not install, execute code, submit jobs, purchase access, change the repository or claim operational readiness. The broad exception-to-END path is already known before either output and must not be hidden from the baseline.

Existing authorised web and GitHub reads are the acquisition tools. No new paid service or external human engagement is authorised. Each task is limited to its named source set and one source-gap follow-up batch; the protocol does not require using every possible read. Review and recording remain mandatory. Offline/stale and inaccessible evidence must remain marked as such.

## Prespecified review

Both conditions must answer the same question, cite inspected support, retain version/scope limits, avoid fabricated execution, preserve known counterevidence, and retain consumer authority. Any material regression in these invariants fails the pair; additional fields or greater length cannot compensate.

SCH specialisation must change at least one substantive research operation: an explicit work/report/version linkage affecting independent-unit counting; a design-specific appraisal that limits transfer of the benchmark threshold; or a status/eligibility check with an honest evidence boundary. Merely printing the pack name or adding headings is insufficient. The review must point to the actual consequence for counting, inference or follow-up.

OSS specialisation must change at least one substantive operation: reconcile setup evidence across code/package/deployment documentation; distinguish maintenance activity from tested readiness with an evidence inventory; or bind a static failure-path observation to an actionable test and returned-result acceptance condition. Repeating a star count or adding a badge is insufficient.

Record every criterion separately as PASS, FAIL, BLOCKED or NOT APPLICABLE with a reason and output locator. Record changes that are absent as absent; do not force a claimed improvement. Preserve exact outputs and hashes. Automated checks establish record integrity and detect specific errors; semantic review establishes only the stated qualitative judgement.

## Interpretation limits

One assistant applies both procedures in a shared session and performs the recorded review. Runs are not blinded, independent, randomised or counterbalanced; carryover and author-reviewer bias are possible. The comparison demonstrates the content and decision effects of applying these design profiles to two actual source-backed tasks. It estimates no causal improvement, error rate, quality score or runtime saving. Later behavioural evaluations require fresh isolated invocations and independent expected outcomes where available. Stage 18/20 installation evidence cannot be inferred from this demonstration.
